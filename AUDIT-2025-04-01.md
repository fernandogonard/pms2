## 🔴 PROBLEMAS BLOQUEANTES (P0) — NO SE PUEDE IR A PRODUCCIÓN

### 1. SCHEMAS DESINCRONIZADOS CON LA REALIDAD

**Este es el problema más grave del sistema.** Los modelos Mongoose no reflejan lo que realmente se guarda en MongoDB.

#### 1.1 Reservation Model — Esquema vs Realidad

**Archivo:** `backend/models/Reservation.js` (28 líneas)

```
ESQUEMA ACTUAL (lo que Mongoose conoce):
  room: ObjectId (ref Room)  ← SINGULAR
  user: ObjectId (ref User)
  name: String
  email: String (required)
  checkIn: Date (required)
  checkOut: Date (required)
  status: enum ['reservada','checkin','checkout','cancelada']
  createdAt: Date
```

```
LO QUE EL CONTROLADOR REALMENTE GUARDA (reservationController.js L290-350):
  tipo: String               ← NO EXISTE EN SCHEMA
  cantidad: Number           ← NO EXISTE EN SCHEMA
  client: ObjectId (ref Client) ← NO EXISTE EN SCHEMA
  pricing: {                 ← NO EXISTE EN SCHEMA
    pricePerNight, totalNights, subtotal, taxes, total, currency
  }
  payment: {                 ← NO EXISTE EN SCHEMA
    status, method, amountPaid
  }
  invoice: {                 ← NO EXISTE EN SCHEMA
    isPaid
  }
  room: Array                ← SCHEMA DICE ObjectId SINGULAR
```

**Impacto:**
- Mongoose no valida `tipo`, `cantidad`, `pricing`, `payment`, `invoice`
- Cualquier typo en el controller se guarda sin error
- No hay valores default para campos críticos de pago
- `room` se usa como Array pero schema dice ObjectId singular
- `billingService.processPayment()` accede a `reservation.pricing.total` y `reservation.payment.amountPaid` — campos que Mongoose no reconoce, causando `undefined` en queries tipadas

#### 1.2 Room Model — Esquema vs Realidad

**Archivo:** `backend/models/Room.js` (27 líneas)

```
ESQUEMA ACTUAL:
  number: Number (required, unique)
  type: String (required)
  active: Boolean (default: true)
```

```
LO QUE EL CÓDIGO ESPERA:
  status: String (7 estados)     ← NO EXISTE EN SCHEMA
  floor: Number                  ← NO EXISTE EN SCHEMA
  outOfService: Boolean          ← NO EXISTE EN SCHEMA
  maintenanceDates: [String]     ← NO EXISTE EN SCHEMA
  cleaningDates: [String]        ← NO EXISTE EN SCHEMA
```

**Impacto:**
- `roomSchema.index({ type: 1, status: 1 })` → índice sobre campo inexistente
- `roomAssignmentService.js` busca `Room.find({ status: 'disponible' })` → siempre retorna vacío si `strict` es true
- `AvailabilityService.js` usa `room.outOfService`, `room.maintenanceDates`, `room.cleaningDates` — campos fantasma
- **Todo el sistema de asignación automática puede estar roto** porque depende de `status`

> **NOTA:** Mongoose con `strict: true` (default) descarta campos no definidos en el schema. Esto significa que `status`, `pricing`, `payment` etc. podrían NO estar guardándose. Si `strict: false` o se usa `$set` directo, se guardan sin validación.

### 2. DUPLICACIÓN DE LÓGICA DE DISPONIBILIDAD

Existen **DOS implementaciones paralelas** del cálculo de disponibilidad:

| Archivo | Enfoque | Usado por |
|---------|---------|-----------|
| `services/availabilityEngine.js` | Transaccional con sesión, cache Map | Tests, import en controller |
| `services/AvailabilityService.js` | Overlay de prioridades, sin sesión | Frontend calendar data |

**Riesgo:** Cada archivo puede calcular disponibilidad **diferente** para la misma fecha. Un cambio en una no se refleja en la otra.

**Acción:** Unificar en UN solo servicio con UNA fuente de verdad.

## 🟠 PROBLEMAS CRÍTICOS (P1) — Deben resolverse antes de producción

### 5. CAMPO `room` — SINGULAR vs ARRAY

El schema de Reservation define:
```javascript
room: { type: mongoose.Schema.Types.ObjectId, ref: 'Room' }  // SINGULAR
```

Pero todo el código lo trata como **Array**:
```javascript
// roomAssignmentService.js:
reservation.room = [...assignedRooms];

// reservationController.js:
if (reserva.room && reserva.room.length > 0)

// AvailabilityService.js:
reservationIncludesRoom(res.room, room._id) // Maneja ambos casos con helper
```

**Impacto:** `populate('room')` no funciona correctamente porque Mongoose espera un ObjectId, no un Array.

| Concepto | En Model | En Controller | En Frontend | En Constants |
|----------|----------|---------------|-------------|--------------|

- `ROOM_STATUS`: `disponible, ocupada, limpieza, mantenimiento`
- Pero `AvailabilityService.js` usa: `fuera_de_servicio, mantenimiento, checkout_hoy, limpieza, checkin_pendiente, ocupada, disponible` (7 estados)
- Y el Room model no tiene `status` definido

### 7. NO HAY GRACEFUL SHUTDOWN

**Archivo:** `backend/server.js`

No maneja señales SIGTERM/SIGINT. Si el proceso se mata:
- Conexiones MongoDB quedan abiertas
- WebSockets no se cierran limpiamente
- Locks en memoria se pierden
- Transacciones pendientes no hacen rollback

## 🎯 CONCLUSIÓN EJECUTIVA

El sistema tiene **buena intención arquitectónica** (separación de capas, constants, logging, security) pero sufre de un problema fundamental: **los modelos de datos no reflejan la realidad del código**. Esto invalida toda la capa de validación de Mongoose y hace que el sistema opere con datos no verificados.

**Antes de agregar cualquier feature nueva (facturación, pagos, channel manager), se DEBEN corregir los schemas.** Construir sobre schemas rotos es construir sobre arena.

### Orden de trabajo recomendado:
1. 🔴 **Fase 0** — Corregir schemas y fundamentos (~1 semana)
2. 🟠 **Fase 1** — Facturación sobre schemas correctos (~1 semana)
3. 🟡 **Fase 2** — Testing para blindar todo lo anterior (~1 semana)
4. 🟢 **Fase 3** — Estabilización y features (~2 semanas)

**Con este plan, el sistema puede pasar de 5.5/10 a 9/10 en 4-5 semanas de trabajo focalizado.**
